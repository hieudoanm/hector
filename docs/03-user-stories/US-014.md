# US-014: Audit financial events

## User Story
**As an** operator,
**I want to** audit all authentication and financial events,
**so that** I can investigate issues and maintain compliance records.

## Acceptance Criteria
- The system records audit events for all authentication actions (login, logout, token refresh).
- The system records audit events for all financial operations (transfer initiation, completion, failure).
- Audit events include: actor, action, resource, timestamp, and correlation ID.
- Audit events do not contain passwords, tokens, or full account numbers.
- Audit logs are durably persisted and can be queried for investigation.

## Technical Implementation Details

### Audit Event Structure
All audit events follow a consistent structure:
```json
{
  "auditId": "uuid (UUID v7)",
  "timestamp": "string (ISO 8601 UTC timestamp)",
  "actor": {
    "type": "string (user | service | system)",
    "identifier": "string (hashed user ID, service name, or system component)",
    "authenticationMethod": "string (jwt | service_account | none) - when applicable"
  },
  "action": "string (specific action being audited)",
  "resource": {
    "type": "string (account | transfer | user | session)",
    "identifier": "string (hashed ID or UUID v7 - never full sensitive data)"
  },
  "context": {
    "requestId": "string (UUID v7)",
    "correlationId": "string (UUID v7)",
    "ipAddress": "string (optional, truncated/pseudonymized for privacy)",
    "userAgent": "string (optional, truncated for privacy)",
    "additionalData": "object (action-specific non-sensitive data)"
  },
  "outcome": {
    "result": "string (success | failure)",
    "errorCode": "string (optional, when failure)",
    "errorMessage": "string (optional, sanitized when failure)"
  }
}
```

### Audit-Worthy Events

#### Authentication Events
1. **User Login**
   - Action: `user.login`
   - Resource: `user` (hashed user ID)
   - Context: Authentication method, IP address (truncated), user agent (truncated)
   - Outcome: Success/failure with appropriate error codes

2. **User Logout**
   - Action: `user.logout`
   - Resource: `user` (hashed user ID)
   - Context: Session information, IP address (truncated)
   - Outcome: Success/failure

3. **Token Refresh**
   - Action: `user.token_refresh`
   - Resource: `user` (hashed user ID)
   - Context: Old token info (jti/hash), IP address (truncated)
   - Outcome: Success/failure

#### Financial Events
1. **Transfer Initiation**
   - Action: `financial.transfer.initiate`
   - Resource: `transfer` (transfer ID)
   - Context: Source account (hashed), destination account (hashed), amount, currency
   - Outcome: Success/failure with error codes

2. **Transfer Completion**
   - Action: `financial.transfer.complete`
   - Resource: `transfer` (transfer ID)
   - Context: Source account (hashed), destination account (hashed), amount, currency
   - Outcome: Success (always success for this event type)

3. **Transfer Failure**
   - Action: `financial.transfer.fail`
   - Resource: `transfer` (transfer ID)
   - Context: Source account (hashed), destination account (hashed), amount, currency, failure reason
   - Outcome: Failure with specific error code and sanitized message

### Implementation Approaches

#### Option 1: Centralised Audit Service (not canonical)
- Separate microservice responsible for receiving and storing audit events
- Services publish audit events to a Kafka topic (`audit-events`)
- Benefits: Decoupling, scalability, specialized storage optimization
- Trade-off: Introduces a service and keyspace outside the canonical microservice set and can create circular dependencies

#### Option 2: Embedded Audit Logging (recommended, canonical)
- Each service writes audit events to an `audit_events` table in **its own keyspace** (`auth_keyspace`, `account_keyspace`, `transfer_keyspace`, `transaction_keyspace`)
- No cross-service keyspace access; each service owns and queries only its own audit events
- Benefits: Simplicity, no external dependency, preserves the no-shared-keyspace boundary

#### Option 3: Hybrid Approach
- Critical financial events additionally projected to a dedicated read model
- Balance of completeness and simplicity

**Recommended**: Option 2 (embedded `audit_events` tables) because the canonical architecture defines `audit_events` within each service keyspace and forbids cross-service keyspace access.

### Database Schema Changes
**Per-service Keyspaces** (canonical)
- Each service owns an `audit_events` table in its own keyspace (`auth_keyspace`, `account_keyspace`, `transfer_keyspace`, `transaction_keyspace`).
- Table: `audit_events`
  - Columns:
    - `audit_id` (UUID v7, primary key, timeuuid component for chronological ordering)
    - `event_type` (text, partition key for efficient querying by type)
    - `timestamp` (timestamp, clustering key for time-based queries)
    - `actor_type` (text)
    - `actor_identifier` (text)
    - `action` (text)
    - `resource_type` (text)
    - `resource_identifier` (text)
    - `request_id` (UUID v7)
    - `correlation_id` (UUID v7)
    - `context_ip_address` (text, pseudonymized)
    - `context_user_agent` (text, truncated)
    - `context_additional_data` (text, JSON)
    - `outcome_result` (text)
    - `outcome_error_code` (text)
    - `outcome_error_message` (text)
- Table: `audit_events_by_user` (for user-specific queries within a service)
  - Similar structure with user identifier as partition key
- Table: `audit_events_by_resource` (for resource-specific queries within a service)
  - Similar structure with resource identifier as partition key

### Security Considerations
- Data minimization: Audit events exclude sensitive data (passwords, tokens, full account numbers)
- Pseudonymization: Identifiers are hashed or truncated to prevent identification while maintaining utility for investigation
- Integrity protection: Audit logs are append-only and cryptographically signed to prevent tampering
- Access controls: Strict role-based access to audit logs (auditors, security personnel only)
- Retention policy: Configurable retention periods based on regulatory requirements
- Secure transmission: Audit events sent via encrypted channels (TLS) if using separate service
- Immutable storage: Once written, audit events cannot be modified or deleted (except per retention policy)
- Location awareness: Audit logs stored in secure, access-controlled environments
- Breach detection: Audit logging of access to audit logs themselves

### Error Handling
- Audit service unavailable: Events buffered locally, retry with exponential backoff
- Local buffer overflow: Oldest events dropped when buffer exceeds threshold (with alert)
- Audit writing failure: Event not lost - retry mechanism ensures eventual persistence
- Partial audit failure: Critical fields (timestamp, event type, outcome) prioritized
- Internal audit system failures: Monitored and alerted separately
- Chain of custody: Maintained even during system failures or maintenance windows

### Test Cases
1. Login success → Audit event recorded with outcome: success
2. Login failure (invalid credentials) → Audit event recorded with outcome: failure
3. Login failure (invalid email format) → Audit event recorded with outcome: failure
4. Logout success → Audit event recorded with outcome: success
5. Token refresh success → Audit event recorded with outcome: success
6. Token refresh failure (expired token) → Audit event recorded with outcome: failure
7. Transfer initiation success → Audit event recorded with outcome: success
8. Transfer initiation failure (insufficient funds) → Audit event recorded with outcome: failure
9. Transfer initiation failure (invalid destination) → Audit event recorded with outcome: failure
10. Transfer completion → Audit event recorded with outcome: success
11. Transfer failure (system error) → Audit event recorded with outcome: failure
12. Verify audit events contain all required fields: actor, action, resource, timestamp, correlation ID
13. Verify no sensitive data in audit events (passwords, tokens, full account numbers)
14. Verify actor identification is appropriately pseudonymized
15. Verify resource identification does not expose full sensitive identifiers
16. Verify timestamp accuracy within acceptable tolerance
17. Verify correlation ID matches request ID from original API call
18. Verify audit events are durably persisted (survive service restarts)
19. Verify audit logs can be queried by time range, event type, user, and resource
20. Verify audit logging performance does not significantly impact request latency
21. Test audit system under high load (peak transaction volumes)
22. Verify audit system recovery after temporary outage
23. Test audit log integrity protection (tampering detection)
24. Verify retention policy enforcement (old events properly archived/deleted)
25. Test audit of service-to-service communications (when applicable)
26. Verify audit events captured for all failure scenarios, not just successes
27. Test audit of administrative/operator actions (when implemented)
28. Verify GDPR/compliance readiness (ability to export/user-specific data)
29. Verify no audit logging of audit system itself to avoid infinite loops
30. Check that audit system does not create circular dependencies

### Dependencies
- All canonical services (Auth, Account, Transfer, Transaction) for event generation and their own `audit_events` tables
- Cassandra database for audit storage (per-service keyspaces)
- Kafka messaging system (only if a downstream projection of audit events is added; not required for the canonical embedded approach)
- Optional: External SIEM/log aggregation system for advanced analysis
