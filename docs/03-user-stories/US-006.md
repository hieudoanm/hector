# US-006: Monitor transfer status

## User Story
**As an** account holder who initiated a transfer,
**I want to** monitor the transfer status,
**so that** I know when the transfer completes or fails.

## Acceptance Criteria
- Given a valid transfer ID, when I poll the status endpoint, then the system returns the current status (pending, processing, completed, failed, reversed).
- Given an unknown transfer ID or a transfer that belongs to another user, when I request status, then the system returns 404 `TRANSFER_NOT_FOUND` without revealing details.
- Given a malformed transfer ID (not a UUID v7), when I request status, then the system returns 400 `VALIDATION_ERROR`.
- The status updates from pending to completed or failed as the Kafka consumer processes the transfer.
- The system provides a transfer status endpoint for polling.

## Technical Implementation Details

### API Endpoint
- **Method**: GET
- **Path**: `/api/v1/transfers/{transferId}`
- **Headers**: 
  - Authorization: Bearer <accessToken>
- **Path Parameters**:
  - `transferId`: UUID v7 of the transfer to check
- **Success Response (200 OK)**:
  ```json
  {
    "transferId": "uuid (UUID v7)",
    "sourceAccountId": "uuid (UUID v7)",
    "destinationAccountId": "uuid (UUID v7)",
    "amountCents": "integer",
    "status": "string (pending | processing | completed | failed | reversed)",
    "createdAt": "string (ISO 8601 UTC timestamp)",
    "updatedAt": "string (ISO 8601 UTC timestamp)",
    "failureReason": "string | null"
  }
  ```
- **Error Responses** (error envelope `{"error":{"code","message","details","requestId"}}`):
  - 400 VALIDATION_ERROR: Malformed transfer ID
  - 401 UNAUTHENTICATED: Missing or invalid access token
  - 401 TOKEN_EXPIRED: Access token expired
  - 404 TRANSFER_NOT_FOUND: Transfer not found or not owned by the authenticated user

### Database Schema Changes
**Transfer Service Keyspace** (builds on US-005):
- Table: `transfers` (no additional columns needed from US-005)
  - All required fields already present

### Security Considerations
- Account ownership verification: Ensure authenticated user owns either source or destination account
- Transfer ID validation: UUID v7 format check
- No transfer details leakage: Same error message for "not found" and "not authorized" to prevent enumeration
- Status transitions follow defined workflow: pending → processing → completed/failed/reversed
- Immutable transfer records: Once created, transfer records are never modified (only status updates via new records or versioning)
- Failure reason sanitization: No sensitive information in the `failureReason` field

### Error Handling
- Missing or invalid access token: Return 401 with error code `UNAUTHENTICATED` and message "Missing or invalid access token"
- Expired access token: Return 401 with error code `TOKEN_EXPIRED` and message "Access token expired"
- Invalid transfer ID format: Return 400 with error code `VALIDATION_ERROR` and message "Invalid transfer ID"
- Transfer not found: Return 404 with error code `TRANSFER_NOT_FOUND` and message "Transfer not found"
- Unauthorized access (user doesn't own source or destination account): Return 404 with error code `TRANSFER_NOT_FOUND` and message "Transfer not found" (avoids enumeration)
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`
- Service unavailable (e.g., Cassandra down): Return 503 with error code `SERVICE_UNAVAILABLE` and Retry-After header

### Test Cases
1. Valid transfer ID for owned account → 200 OK with transfer details
2. Invalid transfer ID format → 400 `VALIDATION_ERROR`
3. Non-existent transfer ID → 404 `TRANSFER_NOT_FOUND`
4. Transfer ID belonging to another user → 404 `TRANSFER_NOT_FOUND` (same message as not found)
5. Transfer in pending status → Returns status: pending
6. Transfer in processing status → Returns status: processing
7. Transfer in completed status → Returns status: completed with null failureReason
8. Transfer in failed status → Returns status: failed with failureReason populated
9. Transfer in reversed status → Returns status: reversed with failureReason populated
10. Timestamp fields present and in ISO 8601 UTC format
11. Source and destination account IDs are valid UUIDs
12. Amount matches what was requested in original transfer
13. Failure reason only present for failed/reversed transfers
14. Concurrent status requests return consistent results
15. Status updates properly reflect Kafka consumer processing
16. Verify no account information leakage in error messages
