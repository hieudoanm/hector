# US-007: Process transfer asynchronously

## User Story
**As the** system,
**I want to** process transfers asynchronously via Kafka consumers,
**so that** the API remains responsive and transfers are processed reliably.

## Acceptance Criteria
- Given a published transfer event, when the Kafka consumer processes it, then it applies the source debit and the destination credit as separate atomic lightweight transactions, coordinating them via saga compensation (a failed credit reverses the debit).
- Given a transfer event, when the consumer processes it, then it updates the transfer status to completed or failed.
- Given duplicate events with the same idempotency key, when the consumer processes them, then it does not cause double debit/credit (idempotent).
- Given a consumer failure mid-processing, when it recovers, then it can safely reprocess the event without causing duplicate transfers.
- Given a successful transfer, when processing completes, then the system records a transaction entry for both source and destination accounts.
- Given a failed transfer (e.g., insufficient funds after validation delay, destination account deleted), when processing fails, then the transfer status is updated to failed and any completed debit is compensated (net-zero balance change).

## Technical Implementation Details

### Kafka Consumer Configuration
- **Topic**: `transfers`
- **Consumer Group**: `transfer-processors`
- **Partitioning Strategy**: Keyed by sourceAccountId (ensures ordered processing per account)
- **Processing Guarantees**: At-least-once delivery with idempotent processing
- **Auto Commit**: Disabled (manual commit after successful processing)
- **Max Poll Records**: 1 (process one event at a time for simplicity and ordering)
- **Session Timeout**: 30 seconds
- **Heartbeat Interval**: 3 seconds

### Processing Workflow
1. Consume `transfer.initiated` event from Kafka
2. Validate event structure and required fields
3. Check idempotency: If already processed (by checking transfer status or dedicated processed events table), acknowledge and skip
4. Update transfer status to `processing` in Transfer Service database
5. Validate source account still has sufficient funds (re-check in case of race conditions)
6. Validate destination account still exists
7. Apply the balance changes as two separate steps (there is no distributed transaction across accounts):
   - Debit source account (single conditional LWT): `UPDATE accounts SET balance_cents = balance_cents - ? WHERE account_id = ? IF balance_cents >= ?` — `applied == false` means insufficient funds
   - Credit destination account (separate statement): `UPDATE accounts SET balance_cents = balance_cents + ? WHERE account_id = ?`
   - If the debit fails, stop (no balances modified). If the debit succeeds but the credit fails, compensate by reversing the debit; the saga guarantees net-zero movement.
8. Update transfer status based on outcome:
   - Success: status = `completed`, updated_at = current timestamp
   - Insufficient funds: status = `failed`, failure_reason = "Insufficient funds"
   - Destination account invalid: status = `failed`, failure_reason = "Destination account invalid"
   - Other errors: status = `failed`, failure_reason = "System error"
9. Publish transfer completion event to Kafka:
   - Topic: `transfers`
   - Event type: `transfer.completed` or `transfer.failed`
   - Includes final status and any failure reason
10. Create transaction records in Transaction Service:
    - Debit transaction: type = debit, amount = negative amount_cents
    - Credit transaction: type = credit, amount = positive amount_cents
11. Acknowledge Kafka message (commit offset)

### Database Schema Changes
**Transfer Service Keyspace** (builds on US-005 and US-006):
- Table: `transfers` (add index on status for efficient querying)
  - No schema changes needed, but ensure proper indexing

**Transaction Service Keyspace** (new service for this user story):
- Keyspace: `transaction_keyspace`
- Table: `transactions`
  - Columns:
    - `transaction_id` (UUID v7, primary key)
    - `account_id` (UUID v7, foreign key to accounts in account service)
    - `type` (text: debit or credit)
    - `amount_cents` (bigint)
    - `counterparty_account_id` (UUID v7, foreign key to accounts)
    - `created_at` (timestamp)
- Table: `audit_events`
  - Records transaction-related audit events (see US-014)
- The Transaction Service owns only `transactions` and `audit_events`; it holds no copy of the Account Service `accounts` table and never reads another service's keyspace.

**Alternative Approach - Event Sourcing for Transactions**:
Instead of deriving account details at read time, Transaction Service could:
1. Subscribe to account.debited and account.credited events from Account Service
2. Build transaction history from these events
3. This would eliminate need for direct database access to Account Service

### Security Considerations
- Idempotent processing: Track processed events to prevent duplicate effects
- Atomic per-account balance updates: Use Cassandra lightweight transactions (compare-and-set) to prevent race conditions; the debit and credit are separate statements coordinated by compensation
- Input validation: Verify all fields in Kafka event before processing
- Amount validation: Re-validate amount limits and positivity
- Account validation: Confirm both accounts exist and are active
- Authorization: Verify the transfer being processed belongs to a legitimate authenticated user (via source account ownership)
- No sensitive data in Kafka events: Only transfer IDs, account IDs, amounts
- Poison message handling: Send repeatedly failing events to the dead-letter topic `transfers.dlq` after max retries
- Consumer resilience: Handle temporary database/Kafka outages gracefully

### Error Handling and Retry Logic
- Transient failures (database timeout, network issue): Retry with exponential backoff (up to 3 attempts)
- Permanent failures (validation errors, insufficient funds): Mark transfer as failed, publish failure event, acknowledge message
- Consumer crashes during processing: On restart, check transfer status to determine if reprocessing is needed
- Duplicate processing detection: Check transfer status before processing; if not pending, acknowledge and skip
- Manual intervention: Provide admin interface to inspect and manually resolve stuck transfers

### Test Cases
1. Valid transfer event → Processes successfully, each account updated by its own atomic LWT, status = completed
2. Insufficient funds during processing → Debit LWT fails, status = failed, no balance changes, failure reason provided
3. Destination account deleted after initiation → Debit succeeds, credit fails, debit is reversed (net-zero balance change), status = failed
4. Duplicate events with same idempotency key → Processed only once, no double accounting
5. Consumer failure after debit but before credit → On recovery, detects incomplete state and processes compensation (reverse debit)
6. Network partition during processing → Retry logic handles temporary failures
7. Maximum concurrent consumers → System scales properly without conflicts
8. Verify lightweight transactions prevent race conditions under high load
9. Transaction records created for both accounts on successful transfer
10. No transaction records created for failed transfers
11. Verify event publishing to Kafka after processing completion
12. Verify idempotency tracking prevents duplicate processing
13. Verify poison message handling after repeated failures
14. Verify no sensitive data in logs or Kafka events
15. Verify proper resource cleanup (connections, transactions) on success and failure
