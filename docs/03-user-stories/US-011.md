# US-011: Handle transfer failures gracefully

## User Story
**As an** account holder,
**I want to** understand why a transfer failed,
**so that** I can correct the problem and retry if appropriate.

## Acceptance Criteria
- Given a transfer that fails, when I check the status, then the system returns a failed status with a safe error message.
- Given a transfer that fails due to insufficient funds, when I check the status, then the error message indicates insufficient funds without revealing account details.
- Given a transfer that fails due to an invalid destination account, when I check the status, then the error message indicates the destination account is invalid without revealing whether it exists.
- Given a transfer that fails due to a system error, when I check the status, then the error message indicates a temporary failure and I can retry.
- Failed transfers do not modify account balances.
- Failed transfers do not create transaction records; their outcome is available from the transfer status endpoint as a failed status with a `failureReason`.

## Technical Implementation Details

### Failure Categories and Responses
The system categorizes transfer failures into specific types to provide appropriate user feedback while maintaining security:

#### 1. Insufficient Funds
- **Detection**: Source account balance < transfer amount at time of processing
- **User Message**: "Insufficient funds to complete this transfer"
- **Technical Details**: 
  - HTTP Status: 400 Bad Request (for pre-check) or transfer status = failed
  - Error Code: INSUFFICIENT_FUNDS
  - `failureReason` field: "Insufficient funds"
  - Account balances: Unchanged
  - Retry Advisory: User should add funds or reduce amount

#### 2. Invalid Destination Account
- **Detection**: Destination account ID does not exist or is inactive
- **User Message**: "Unable to process transfer to the specified account"
- **Technical Details**:
  - HTTP Status: 404 Not Found (for pre-check) or transfer status = failed  
  - Error Code: ACCOUNT_NOT_FOUND
  - `failureReason` field: "Destination account invalid"
  - Account balances: Unchanged
  - Retry Advisory: User should verify destination account information
  - Security Note: Same message used for "account does not exist" and "account exists but not accessible" to prevent enumeration

#### 3. System Error
- **Detection**: Unexpected failure during processing (database timeout, network issue, etc.)
- **User Message**: "Temporary system error. Please try again later."
- **Technical Details**:
  - HTTP Status: 503 Service Unavailable (for transient errors) or transfer status = failed
  - Error Code: SERVICE_UNAVAILABLE
  - `failureReason` field: "System error - please try again"
  - Account balances: Unchanged
  - Retry Advisory: User can safely retry after brief delay
  - Logging: Detailed error logged internally for engineering investigation

#### 4. Validation Error
- **Detection**: Invalid request parameters (amount ≤ 0, same account, etc.)
- **User Message**: Specific to validation failure (e.g., "Amount must be greater than zero")
- **Technical Details**:
  - HTTP Status: 400 Bad Request
  - Error Code: VALIDATION_ERROR (or the more specific INVALID_AMOUNT / SAME_ACCOUNT where applicable)
  - `failureReason` field: Specific validation error
  - Account balances: Unchanged
  - Retry Advisory: User should correct the invalid input

### API Endpoints Affected
- **Transfer Initiation (`POST /api/v1/transfers`)**: Returns failure information in response body for synchronous failures
- **Transfer Status (`GET /api/v1/transfers/{transferId}`)**: Returns `failureReason` field for asynchronous failures

### Database Schema Changes
**Transfer Service Keyspace** (builds on US-005, US-006, and US-007):
- Table: `transfers` (failure_reason column already defined in US-006)
  - failure_reason: text, nullable
  - Used to store specific failure information for failed transfers

### Security Considerations
- Information leakage prevention: Failure messages carefully crafted to avoid revealing sensitive account information
- Consistent error messaging: Same user-facing message for different underlying causes that could leak information
- No sensitive data in failureReason: Field contains only user-safe information
- Logging separation: User-safe messages in failureReason, detailed diagnostic information in internal logs only
- Retry safety: Clear indication of which errors are safe to retry (system errors) vs which require user action (insufficient funds, invalid account)
- Temporal safety: Failure reasons do not change over time in a way that could be exploited for probing

### Error Handling Flow
#### Synchronous Failures (detected during transfer initiation)
1. Validate request format and parameters
2. Validate source account ownership and balance
3. Validate destination account existence
4. If any validation fails, return appropriate error response immediately
5. No transfer record created, no Kafka event published

#### Asynchronous Failures (detected during processing by Kafka consumer)
1. Transfer record created with status = pending
2. Kafka event published: transfer.initiated
3. Consumer processes event
4. If processing fails, update transfer record:
   - status = failed
   - failureReason = appropriate safe message
   - updated_at = current timestamp
5. Publish failure event: transfer.failed
6. Create transaction records only for successful transfers

### Test Cases
1. Insufficient funds failure → Status: failed, failureReason: "Insufficient funds"
2. Invalid destination account → Status: failed, failureReason: "Destination account invalid" 
3. Same source and destination account → 400 Bad Request during initiation (`SAME_ACCOUNT`)
4. Amount ≤ 0 → 400 Bad Request during initiation (`INVALID_AMOUNT`)
5. System error during processing → Status: failed, failureReason: "System error - please try again"
6. Network timeout during processing → Status: failed, failureReason: "System error - please try again"
7. Verify account balances unchanged after any failure
8. Verify no failed transfers create transaction records
9. Verify successful transfers create both debit and credit transaction records
10. Verify failureReason field is null for successful/pending transfers
11. Verify failureReason only populated for failed transfers
12. Test retry behavior: System errors allow successful retry after delay
13. Test retry behavior: Insufficient funds requires fund addition before retry succeeds
14. Test retry behavior: Invalid destination requires correction before retry succeeds
15. Verify failure messages do not contain account numbers, balances, or other sensitive data
16. Verify consistent error messages for security-equivalent failure modes
17. Test failure handling under high load and concurrent operations
18. Verify proper cleanup of resources (database connections, etc.) on failure paths
19. Verify failure events published to Kafka contain appropriate information for downstream systems
20. Verify transaction service properly handles failed transfer events (creates no records)
