# US-013: Monitor system health

## User Story
**As an** operator,
**I want to** monitor system health and performance,
**so that** I can detect and respond to issues.

## Acceptance Criteria
- The system exposes a `/healthz` endpoint for liveness checks.
- The system exposes a `/readyz` endpoint for readiness checks (Cassandra, Kafka connectivity).
- Health endpoints do not require authentication but do not expose sensitive information.
- The system emits structured JSON logs for all requests with correlation IDs.
- The system publishes metrics: request latency (histogram), error rate, active users, transfer throughput, and Kafka consumer lag.
- Alerts are configured for: error rate > 1%, p99 latency > 2s, Kafka consumer lag > 1000, and disk usage > 80%.

## Technical Implementation Details

### Health Check Endpoints
#### Liveness Probe (/healthz)
- **Method**: GET
- **Path**: `/healthz` (served by the API Gateway at the root, outside `/api/v1`)
- **Authentication**: None (public endpoint)
- **Response (200 OK)**:
  ```json
  {
    "status": "string (healthy | unhealthy)",
    "timestamp": "string (ISO 8601 UTC timestamp)"
  }
  ```
- **Implementation**: 
  - Returns healthy if the service process is running and able to accept requests
  - Does not check dependencies (database, Kafka, etc.)
  - Used by orchestration platforms (Kubernetes) to determine if service should be restarted
  - Unhealthy response (503) if service is unable to process requests at all

#### Readiness Probe (/readyz)
- **Method**: GET
- **Path**: `/readyz` (served by the API Gateway at the root, outside `/api/v1`)
- **Authentication**: None (public endpoint)
- **Response (200 OK)**:
  ```json
  {
    "status": "string (ready | not_ready)",
    "timestamp": "string (ISO 8601 UTC timestamp)",
    "checks": {
      "cassandra": "string (healthy | unhealthy)",
      "kafka": "string (healthy | unhealthy)",
      "diskSpace": "string (healthy | unhealthy)"
    }
  }
  ```
- **Response (503 Service Unavailable)**:
  ```json
  {
    "status": "not_ready",
    "timestamp": "string (ISO 8601 UTC timestamp)",
    "checks": {
      "cassandra": "string (healthy | unhealthy)",
      "kafka": "string (healthy | unhealthy)", 
      "diskSpace": "string (healthy | unhealthy)"
    }
  }
  ```
- **Implementation**:
  - Cassandra check: Simple query to verify connectivity and basic functionality
  - Kafka check: Producer metadata request to verify broker connectivity
  - Disk space check: Verify sufficient space for logs and temporary files (>15% free)
  - Returns ready only if all checks pass
  - Used by orchestration platforms to determine if service should receive traffic

### Structured Logging
- **Format**: JSON lines (one JSON object per line)
- **Fields**:
  - `timestamp`: ISO 8601 UTC timestamp
  - `level`: log level (debug, info, warn, error)
  - `message`: log message
  - `service`: service name (auth, account, transfer, transaction, gateway)
  - `requestId`: UUID v7 for request tracing
  - `correlationId`: UUID v7 for distributed tracing (may equal requestId)
  - `userId`: UUID v7 (hashed or truncated for privacy) - when available
  - `endpoint`: API endpoint being accessed
  - `method`: HTTP method
  - `statusCode`: HTTP status code (for response logs)
  - `latencyMs`: request processing time in milliseconds
  - Optional fields based on context:
    - `errorType`: error classification
    - `errorMessage`: sanitized error message
    - `accountId`: account identifier (hashed/truncated) - when relevant
    - `transferId`: transfer identifier - when relevant
- **Examples**:
  ```json
  {"timestamp":"2026-10-15T10:30:00Z","level":"info","message":"Request processed","service":"gateway","requestId":"uuid","correlationId":"uuid","endpoint":"/api/v1/accounts/{accountId}/balance","method":"GET","statusCode":200,"latencyMs":45}
  ```
  ```json
  {"timestamp":"2026-10-15T10:30:01Z","level":"error","message":"Database connection failed","service":"account","requestId":"uuid","correlationId":"uuid","errorType":"dependencyUnavailable","errorMessage":"Database unavailable"}
  ```

### Metrics Collection
#### Request Latency Histogram
- **Buckets**: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1000ms, 2500ms, 5000ms]
- **Labels**: 
  - service: service name
  - endpoint: API endpoint
  - method: HTTP method
  - statusCode: HTTP status code
- **Aggregation**: 5-minute windows for alerting

#### Error Rate
- **Definition**: Percentage of requests returning 4xx or 5xx status codes
- **Labels**:
  - service: service name
  - errorType: clientError (4xx) or serverError (5xx)
- **Calculation**: (error_requests / total_requests) * 100

#### Active Users
- **Definition**: Number of unique users with activity in the last 5 minutes
- **Implementation**: 
  - Sliding window counter using Redis or Cassandra time-series tables
  - User identified by hashed user ID for privacy
  - Updated on each authenticated request

#### Transfer Throughput
- **Definition**: Number of completed transfers per unit time
- **Labels**:
  - direction: incoming, outgoing, internal (same currency)
  - currency: ISO 4217 code
- **Measurement**: Count of transfer.completed events processed

#### Kafka Consumer Lag
- **Definition**: Difference between current log end offset and consumer group offset
- **Labels**:
  - topic: Kafka topic name
  - consumerGroup: consumer group identifier
  - partition: partition number
- **Measurement**: Number of messages lagging behind

### Alerting Rules
Configured in monitoring system (Prometheus/Alerthttp or equivalent):

1. **High Error Rate**:
   ```
   ALERT HighErrorRate
   IF (sum(rate(http_requests_total{status=~"4..|5.."}[5m])) / sum(rate(http_requests_total[5m]))) > 0.01
   FOR 5m
   LABELS { severity = "warning" }
   ANNOTATIONS = {
     summary = "High error rate detected",
     description = "Error rate is above 1% for more than 5 minutes."
   }
   ```

2. **High Latency**:
   ```
   ALERT HighLatency
   IF histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service, endpoint)) > 2
   FOR 5m
   LABELS { severity = "warning" }
   ANNOTATIONS = {
     summary = "High p99 latency detected",
     description = "99th percentile request latency is above 2 seconds for more than 5 minutes."
   }
   ```

3. **High Kafka Consumer Lag**:
   ```
   ALERT HighKafkaLag
   IF sum(kafka_consumer_group_lag) > 1000
   FOR 5m
   LABELS { severity = "warning" }
   ANNOTATIONS = {
     summary = "High Kafka consumer lag detected",
     description = "Kafka consumer lag is above 1000 messages for more than 5 minutes."
   }
   ```

4. **Low Disk Space**:
   ```
   ALERT LowDiskSpace
   IF (node_filesystem_size_bytes - node_filesystem_free_bytes) / node_filesystem_size_bytes > 0.8
   FOR 5m
   LABELS { severity = "critical" }
   ANNOTATIONS = {
     summary = "Low disk space detected",
     description = "Disk usage is above 80% for more than 5 minutes."
   }
   ```

### Database Schema Changes
No additional schema changes required - health checks use existing database connectivity tests.

### Security Considerations
- Information minimization: Health endpoints expose only service status, no sensitive data
- Authentication exclusion: Intentionally public for orchestration systems, but contain no sensitive information
- Logging privacy: Structured logs exclude sensitive data (passwords, tokens, full account numbers)
- Metrics security: No sensitive labels or values in exported metrics
- Denial of service protection: Health endpoints designed to be lightweight and resistant to abuse
- Information leakage prevention: Health check details do not reveal internal architecture weaknesses that could be exploited

### Error Handling
- Health endpoint failures: Return 503 Service Unavailable with appropriate JSON error response
- Logging failures: Fallback to stderr/stdout, trigger internal alerts
- Metrics publishing failures: Buffer locally, retry with exponential backoff, trigger internal alerts
- Alerting system failures: Monitored by separate external system

### Test Cases
1. Healthy service → /healthz returns 200 OK with status: healthy
2. Unhealthy service (crashed/hung) → /healthz returns 503 or connection refused
3. Service ready (all dependencies healthy) → /readyz returns 200 OK with status: ready
4. Service not ready (Cassandra down) → /readyz returns 503 with cassandra: unhealthy
5. Service not ready (Kafka down) → /readyz returns 503 with kafka: unhealthy
6. Service not ready (low disk space) → /readyz returns 503 with diskSpace: unhealthy
7. Structured logging: All requests produce valid JSON log entries
8. Log fields present: timestamp, level, message, service, requestId at minimum
9. Metrics collection: Latency histograms populated with appropriate values
10. Error rate calculation: Increases when 4xx/5xx responses occur
11. Active users count: Increases with unique user activity, decreases after inactivity
12. Transfer throughput: Increases with completed transfers
13. Kafka consumer lag: Increases when consumers fall behind, decreases when they catch up
14. Alert triggering: Alerts fire when conditions met for required duration
15. Alert resolution: Alerts clear when conditions return to normal
16. Alert suppression: Repeated alerts for same issue respect suppression intervals
17. Log privacy: No sensitive data (PII, credentials, tokens) in structured logs
18. Metrics security: No sensitive information in metric labels or values
19. Health endpoint performance: Responds quickly even under load
20. Dependency check accuracy: Correctly reports health of Cassandra and Kafka connections
21. Verify no authentication required for health endpoints
22. Verify sensitive information not exposed in any health check response
23. Test alerting system integration (if applicable)
24. Verify graceful degradation when monitoring components fail

### Dependencies
- All services (each implements its own health checks)
- Cassandra database (for readiness check)
- Kafka messaging system (for readiness check)
- Monitoring system (Prometheus, Grafana, Alertmanager, or equivalent)
- Optional: Redis or Cassandra for active user counting
