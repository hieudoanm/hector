# US-010: Prevent duplicate transfers

## User Story
**As the** system,
**I want to** enforce idempotency for mutating operations, requiring it for transfers,
**so that** network retries do not cause duplicate financial operations.

## Acceptance Criteria
- Given a transfer request with an idempotency key, when submitted multiple times, then only one transfer is created and the same transfer ID is returned.
- Given a transfer request with a missing `Idempotency-Key` header, when submitted, then the system rejects it with `400 VALIDATION_ERROR` (the header is required for transfers).
- Given duplicate events in Kafka with the same idempotency key, when the consumer processes them, then balances are only debited/credited once.
- Idempotency keys are recorded with their operation type in the owning service's keyspace and scoped per operation type.
- Idempotency keys expire after a configurable period (e.g., 24 hours) to allow retries for legitimate new operations.

## Technical Implementation Details

### Idempotency Key Format
- **Format**: UUID v4 or cryptographically secure random string (minimum 32 characters)
- **Header**: `Idempotency-Key: <unique-value>`
- **Length**: Maximum 255 characters
- **Validation**: Must match pattern `[a-zA-Z0-9\-_]+` (alphanumeric, hyphen, underscore)
- **Uniqueness**: The key is the primary key of the owning service's `idempotency_keys` table; clients generate a fresh key per operation

### API Endpoints Supporting Idempotency
`Idempotency-Key` is **required** for the MVP's financial mutation and optional elsewhere:
1. POST `/api/v1/transfers` — **required**
2. POST `/api/v1/register`, `/api/v1/login`, `/api/v1/refresh`, `/api/v1/logout` — not required in the MVP; each is safe to retry without a key (idempotent by nature or token-rotation semantics), and may adopt the header later.
3. Future financial mutations — required, following the transfer pattern.

### Database Schema Changes
Only the Transfer Service owns an idempotency store in the MVP; its authoritative shape is defined in [`05-data-model/transfer-service`](../05-data-model/transfer-service/README.md#idempotency_keys) and US-005.

**Transfer Service Keyspace**
- Table: `idempotency_keys`
  - Columns: `idempotency_key` (text, primary key), `operation_type` (text, e.g. `transfer`), `resource_id` (UUID v7), `request_hash` (text), `response_status` (int), `response_body` (text), `expires_at` (timestamp, `USING TTL`), `created_at` (timestamp)

Auth and Transaction services do not maintain idempotency tables in the MVP. If a future mutating endpoint needs one, it adds an `idempotency_keys` table (same shape) to its own keyspace — never a shared or cross-service table.

### Implementation Details
#### Request Processing Flow
1. Extract the `Idempotency-Key` header (never a body field)
2. For `POST /api/v1/transfers`, a missing or malformed key is rejected with `400 VALIDATION_ERROR`. For other mutating endpoints the key is optional; if absent, process normally (no idempotency guarantee)
3. If key provided:
   - Validate key format and length
   - Check if the key exists in the idempotency table:
     - If exists and not expired with the **same** payload: Return the cached response immediately
     - If exists and not expired with a **different** payload: Return 409 `IDEMPOTENCY_KEY_EXISTS`
     - If exists and expired: Delete old entry, process normally
     - If not exists: Process request, then store result in idempotency table
4. After successful processing, store response in idempotency table with expiration timestamp
5. Set Idempotency-Key header in response (echo back the key used)

#### Response Caching
- Cache entire response body and status code
- Do not cache headers (except Idempotency-Key which is echoed back)
- Cache duration: Configurable, default 24 hours
- Storage efficient: Only store successful responses (2xx) or deterministic errors (4xx where safe)
- For non-deterministic errors (5xx), do not cache - allow retry

#### Kafka Event Idempotency
- **Transfer Service Consumer**:
  - Before processing transfer.initiated event, check if already processed
  - Mechanism: 
    - Option 1: Check transfer status - if not pending, assume already processed
    - Option 2: Maintain separate processed events table with (event_id, processed_at)
    - Option 3: Use idempotency key from original request if included in event
  - Recommended: Include original idempotency key in transfer.initiated event, then check against it
- **Account Service Consumer**:
  - Similar approach for account.debit/requested and account.credit/requested events
  - Check if account operation already applied for given transfer/idempotency key combination

### Security Considerations
- Idempotency key validation: Prevent injection attacks through header parsing
- Storage protection: Idempotency table access controlled like other sensitive data
- Key expiration: Automatic cleanup of expired keys to prevent unbounded growth
- No sensitive data in cached responses: Scrub or encrypt sensitive fields if necessary
- Rate limiting consideration: Idempotency requests still count toward rate limits (prevents abuse)
- Key uniqueness: Ensure proper uniqueness constraints in database tables

### Error Handling
- Invalid Idempotency-Key format: Return 400 with error code `VALIDATION_ERROR` and message "Invalid Idempotency-Key format"
- Idempotency key reused with a different payload: Return 409 with error code `IDEMPOTENCY_KEY_EXISTS` and message "Idempotency key already used"
- Internal server errors during idempotency lookup/storage: Return 500 with error code `INTERNAL_ERROR`
- Idempotency lookup/storage failures on `POST /api/v1/transfers`: **fail closed** — return 503 `SERVICE_UNAVAILABLE` rather than risk a duplicate financial operation. For other (non-financial) mutating endpoints, fail open and process normally.

### Test Cases
1. Request with valid Idempotency-Key → Processes normally, caches response
2. Identical request with same Idempotency-Key → Returns cached response, same status code and body
3. Different request with same Idempotency-Key → 409 `IDEMPOTENCY_KEY_EXISTS` (protects against key reuse with a different payload)
4. Request with invalid Idempotency-Key format → 400 `VALIDATION_ERROR`
5. `POST /api/v1/transfers` with missing Idempotency-Key → 400 `VALIDATION_ERROR`; non-financial mutating endpoints with no key → processed normally (no idempotency guarantee)
6. Expired Idempotency-Key → Processes normally, creates new cache entry
7. Concurrent requests with same Idempotency-Key → First processes and caches, others return cached response
8. POST `/api/v1/transfers` with Idempotency-Key → Caches transfer response
9. Duplicate POST `/api/v1/transfers` with same key and same payload → Returns same transfer ID (202 Accepted)
10. Kafka duplicate events with same Idempotency-Key → Processed only once
11. Mixed case sensitivity in Idempotency-Key → Treated as different keys (unless specified otherwise)
12. Special characters in Idempotency-Key → Only alphanumeric, hyphen, underscore allowed
13. Very long Idempotency-Key (>255 chars) → 400 Bad Request
14. Verify cached responses match original responses exactly
15. Verify no sensitive data leakage in cached responses
16. Verify automatic cleanup of expired idempotency keys
17. Verify keys are scoped per operation type within the owning service's keyspace (no cross-operation collisions)
18. Test required idempotency for `POST /api/v1/transfers` and optional handling on other mutating endpoints
19. Verify idempotency works correctly under high concurrency
20. Verify transfers fail closed (503 `SERVICE_UNAVAILABLE`) when idempotency storage is temporarily unavailable
