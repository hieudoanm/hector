# US-002: Log in to an existing account

## User Story
**As a** registered user,
**I want to** log in with my email and password,
**so that** I can access my account and perform banking operations.

## Acceptance Criteria
- Given valid credentials, when I log in, then I receive a JWT access token (RS256, 15 min expiry) and an opaque refresh token (7 day expiry, stored server-side only as a SHA-256 hash).
- Given invalid credentials, when I log in, then the system rejects the request without revealing whether the email exists.
- Given 5 failed login attempts within 15 minutes, when I attempt to log in again within that same 15-minute window, then the system rate-limits the request with 429 `RATE_LIMITED` (each of the 5 failed attempts itself returns 401 `INVALID_CREDENTIALS`).
- Given a valid refresh token, when I exchange it at `/api/v1/refresh`, then I receive a new access token.
- Given a successful login, when I access protected endpoints, then my JWT access token grants me access.
- Given an expired access token, when I attempt to use it, then the system rejects it with 401 `TOKEN_EXPIRED` and I can use my refresh token to obtain a new access token.
- Given a refresh token that is expired, revoked or already rotated, when I attempt to refresh, then the system rejects the request with 401 `INVALID_REFRESH_TOKEN`.

## Technical Implementation Details

### API Endpoint
- **Method**: POST
- **Path**: `/api/v1/login`
- **Headers**: 
  - Content-Type: application/json
- **Request Body**:
  ```json
  {
    "email": "string (valid email format)",
    "password": "string"
  }
  ```
- **Success Response (200 OK)**:
  ```json
  {
    "accountId": "uuid (UUID v7)",
    "userId": "uuid (UUID v7)",
    "accessToken": "string (JWT RS256, 15 min expiry)",
    "refreshToken": "string (opaque, 7 day expiry)",
    "tokenType": "Bearer",
    "expiresIn": 900
  }
  ```
- **Error Responses** (error envelope `{"error":{"code","message","details","requestId"}}`):
  - 400 VALIDATION_ERROR: Invalid email format
  - 401 INVALID_CREDENTIALS: Invalid email or password
  - 429 RATE_LIMITED: Failed-login lockout (5 per 15 min) or auth rate limit (100 req/min/IP)

### Token Refresh Endpoint
- **Method**: POST
- **Path**: `/api/v1/refresh`
- **Headers**:
  - Content-Type: application/json
- **Request Body**:
  ```json
  {
    "refreshToken": "string (opaque refresh token issued at login or registration)"
  }
  ```
- **Success Response (200 OK)**: same token shape as the login response (`accountId`, `userId`, `accessToken`, `refreshToken`, `tokenType`, `expiresIn`); refresh token rotation issues a new opaque refresh token and revokes the presented one.
- **Error Responses**:
  - 401 INVALID_REFRESH_TOKEN: Missing, malformed, expired, revoked or already-used refresh token
  - 429 RATE_LIMITED: Rate limit exceeded

### Database Schema Changes
**Auth Service Keyspace** (builds on US-001):
- Table: `users` (no changes needed from US-001)
- Table: `refresh_tokens` (no changes needed from US-001)
- Table: `login_attempts` (new)
  - Columns:
    - `id` (timeuuid, primary key)
    - `email_hash` (text, hashed email for privacy)
    - `attempted_at` (timestamp)
    - `ip_address` (inet)
    - `successful` (boolean)

### Security Considerations
- Password verification using Argon2id constant-time comparison to prevent timing attacks
- Rate limiting (two independent limits, both returning 429 `RATE_LIMITED` with `Retry-After`, whichever triggers first):
  - Request-volume limit: 100 requests/minute per IP address for all auth endpoints (`/api/v1/register`, `/api/v1/login`, `/api/v1/refresh`, `/api/v1/logout`)
  - Failed-login lockout: 5 failed logins within 15 minutes from the same IP address (or against the same hashed email) locks further login attempts for the remainder of the 15-minute window; the 5 failed attempts each return 401 `INVALID_CREDENTIALS`, the 6th and subsequent attempts inside the window return 429 `RATE_LIMITED`
- Failed attempt tracking: Clear login_attempts older than 15 minutes
- Access tokens are JWTs signed with RS256 using Auth Service's private key
- Access token expiration: 15 minutes (900 seconds), returned as `expiresIn`
- Refresh token expiration: 7 days
- Refresh tokens are opaque random strings (not JWTs) stored as SHA-256 hashes in the database (never bcrypt) to prevent token theft even if the keyspace is read
- Refresh token rotation: On use, generate new refresh token and invalidate old one

### Error Handling
- Invalid email format: Return 400 with error code `VALIDATION_ERROR` and message "Invalid email format"
- Invalid credentials: Return 401 with error code `INVALID_CREDENTIALS` and message "Invalid credentials" (identical for unknown email and wrong password)
- Expired access token on a protected endpoint: Return 401 with error code `TOKEN_EXPIRED` and message "Access token expired"
- Missing or malformed access token on a protected endpoint: Return 401 with error code `UNAUTHENTICATED` and message "Missing or invalid access token"
- Invalid, expired or revoked refresh token on `/api/v1/refresh`: Return 401 with error code `INVALID_REFRESH_TOKEN` and message "Invalid refresh token"
- Rate limit or lockout exceeded: Return 429 with error code `RATE_LIMITED` and message "Too many failed login attempts" and Retry-After header
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`

### Test Cases
1. Valid login with correct credentials → 200 OK with access and refresh tokens
2. Login with incorrect password → 401 Unauthorized
3. Login with non-existent email → 401 Unauthorized (same message as incorrect password)
4. Login with invalid email format → 400 Bad Request
5. 5 consecutive failed logins from same IP → attempts 1–5 each return 401 `INVALID_CREDENTIALS`, subsequent attempts within the 15-minute window return 429 `RATE_LIMITED`
6. Successful login after rate limit period → 200 OK
7. Expired access token → 401 `TOKEN_EXPIRED` when accessing protected endpoints
8. Valid refresh token → New access token issued via `POST /api/v1/refresh`
9. Expired, revoked or reused refresh token → 401 `INVALID_REFRESH_TOKEN` when attempting to refresh
10. Concurrent login attempts → Each processed separately with proper rate limiting
11. Verify refresh tokens are stored as SHA-256 hashes (not plaintext, not bcrypt) in database
12. Verify login attempts are tracked and cleaned up
