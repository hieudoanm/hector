# US-005: Initiate a transfer to another account

## User Story
**As an** authenticated account holder,
**I want to** transfer funds to another account,
**so that** I can send money to others.

## Acceptance Criteria
- Given a valid access token, sufficient funds, a valid destination account ID, and a positive amount, when I initiate a transfer, then the system accepts the request with `202 Accepted`, returns a transfer ID with initial status `pending`, and processes it asynchronously.
- Given insufficient funds, when I initiate a transfer, then the system rejects the request with 400 `INSUFFICIENT_FUNDS`.
- Given an invalid destination account ID, when I initiate a transfer, then the system rejects the request with 404 `ACCOUNT_NOT_FOUND` without revealing whether the account exists.
- Given a transfer to the same account (source == destination), when I initiate, then the system rejects the request with 400 `SAME_ACCOUNT`.
- Given a transfer with amount ≤ 0, when I initiate, then the system rejects the request with 400 `INVALID_AMOUNT`.
- Given a valid transfer request, when submitted, then the system publishes a transfer event to the `transfers` Kafka topic with all transaction details (source account, destination account, amount, idempotency key, correlation ID).
- Given duplicate transfer requests with the same idempotency key and identical payload, when submitted, then the system returns the cached response (same transfer ID) without creating a duplicate transfer; a reused key with a different payload returns 409 `IDEMPOTENCY_KEY_EXISTS`.

## Technical Implementation Details

### API Endpoint
- **Method**: POST
- **Path**: `/api/v1/transfers`
- **Headers**: 
  - Authorization: Bearer <accessToken>
  - Idempotency-Key: <unique-string> (required; 1–255 chars matching `[a-zA-Z0-9_-]`; never sent in the body)
  - Content-Type: application/json
- **Request Body** (the source account is derived server-side from the authenticated user and is not a field):
  ```json
  {
    "destinationAccountId": "uuid (UUID v7)",
    "amountCents": "integer (> 0 and <= 9,999,999,999)"
  }
  ```
- **Success Response (202 Accepted)**:
  ```json
  {
    "transferId": "uuid (UUID v7)",
    "status": "string (pending | processing | completed | failed | reversed)",
    "amountCents": "integer",
    "sourceAccountId": "uuid (UUID v7)",
    "destinationAccountId": "uuid (UUID v7)",
    "createdAt": "string (ISO 8601 UTC timestamp)",
    "updatedAt": "string (ISO 8601 UTC timestamp)",
    "failureReason": "string | null"
  }
  ```
- **Error Responses** (error envelope `{"error":{"code","message","details","requestId"}}`):
  - 400 VALIDATION_ERROR: Malformed body, invalid UUID, missing required fields, or missing/invalid `Idempotency-Key` header
  - 400 INVALID_AMOUNT: Amount ≤ 0 or above the maximum limit
  - 400 SAME_ACCOUNT: Source account equals destination account
  - 400 INSUFFICIENT_FUNDS: Source account has insufficient funds
  - 401 UNAUTHENTICATED: Missing or invalid access token
  - 401 TOKEN_EXPIRED: Access token expired
  - 404 ACCOUNT_NOT_FOUND: Source account not found or destination account invalid
  - 409 IDEMPOTENCY_KEY_EXISTS: Idempotency key reused with a different payload
  - 429 RATE_LIMITED: Authenticated rate limit exceeded (1000 req/min/user)

### Database Schema Changes
**Transfer Service Keyspace**
- Table: `transfers`
  - Columns:
    - `transfer_id` (UUID v7, primary key)
    - `source_account_id` (UUID v7, foreign key to accounts)
    - `destination_account_id` (UUID v7, foreign key to accounts)
    - `amount_cents` (bigint)
    - `status` (text: pending, processing, completed, failed, reversed)
    - `created_at` (timestamp)
    - `updated_at` (timestamp)
- Table: `idempotency_keys` (for transfer initiation; authoritative shape in [`05-data-model/transfer-service`](../05-data-model/transfer-service/README.md#idempotency_keys))
  - Columns:
    - `idempotency_key` (text, primary key)
    - `operation_type` (text, e.g. `transfer`)
    - `resource_id` (UUID v7, e.g. the `transfer_id`)
    - `request_hash` (text, hash of the request payload — detects key reuse with a different payload)
    - `response_status` (int, cached HTTP status)
    - `response_body` (text, cached response body)
    - `expires_at` (timestamp, `USING TTL`)
    - `created_at` (timestamp)

### Security Considerations
- Account ownership verification: Ensure authenticated user owns source account
- Destination account validation: Check if account exists without revealing information to unauthorized users
- Amount validation: Positive integer in cents, within allowed limits
- Same-account prevention: Source and destination must be different accounts
- Idempotency key validation: UUID or secure random string, expires after 24 hours; repeating the same key with the same payload returns the cached response, while reusing the key with a different payload returns 409 `IDEMPOTENCY_KEY_EXISTS`
- Use lightweight transactions for balance verification and transfer creation to prevent race conditions
- Publish events to Kafka only after local validation and transfer record creation
- No sensitive data (passwords, tokens) in logs or Kafka messages

### Error Handling
- Missing or invalid access token: Return 401 with error code `UNAUTHENTICATED` and message "Missing or invalid access token"
- Expired access token: Return 401 with error code `TOKEN_EXPIRED` and message "Access token expired"
- Invalid request body (malformed JSON, missing fields, invalid UUID): Return 400 with error code `VALIDATION_ERROR` and descriptive message
- Amount ≤ 0 or above the maximum: Return 400 with error code `INVALID_AMOUNT` and message "Amount must be greater than zero and within the allowed limit"
- Source account not found or not owned by the authenticated user: Return 404 with error code `ACCOUNT_NOT_FOUND` and message "Account not found" (avoids enumeration)
- Destination account invalid: Return 404 with error code `ACCOUNT_NOT_FOUND` and message "Destination account not found" (avoids enumeration)
- Source account equals destination account: Return 400 with error code `SAME_ACCOUNT` and message "Cannot transfer to same account"
- Insufficient funds: Return 400 with error code `INSUFFICIENT_FUNDS` and message "Insufficient funds"
- Idempotency key reused with a different payload: Return 409 with error code `IDEMPOTENCY_KEY_EXISTS` and message "Idempotency key already used"
- Rate limit exceeded: Return 429 with error code `RATE_LIMITED` and Retry-After header
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`
- Service unavailable (e.g., Cassandra/Kafka down): Return 503 with error code `SERVICE_UNAVAILABLE` and Retry-After header

### Event Publishing (to Kafka)
- Topic: `transfers` (failed events are routed to the dead-letter topic `transfers.dlq`)
- Key: sourceAccountId (string) - for partitioning by account
- Value: JSON with transfer details
  ```json
  {
    "transferId": "uuid",
    "sourceAccountId": "uuid",
    "destinationAccountId": "uuid",
    "amountCents": "integer",
    "idempotencyKey": "string (required for transfers)",
    "correlationId": "uuid",
    "timestamp": "ISO 8601 UTC timestamp"
  }
  ```
- Event type: `transfer.initiated`

### Test Cases
1. Valid transfer request → 202 Accepted with transfer ID and pending status
2. Insufficient funds → 400 `INSUFFICIENT_FUNDS` with clear error message
3. Invalid destination account ID → 404 `ACCOUNT_NOT_FOUND` (generic message)
4. Transfer to same account → 400 `SAME_ACCOUNT`
5. Amount ≤ 0 → 400 `INVALID_AMOUNT`
6. Missing required fields → 400 `VALIDATION_ERROR`
7. Invalid UUID format for account IDs → 400 `VALIDATION_ERROR`
8. Valid request with idempotency key → 202 Accepted
9. Duplicate request with same idempotency key and same payload → 202 Accepted (same transfer ID); same key with a different payload → 409 `IDEMPOTENCY_KEY_EXISTS`
10. Concurrent transfer requests with same source account → Processed sequentially with proper balance checking
11. Maximum allowed amount (9,999,999,999 cents) → 202 Accepted
12. Amount exceeding maximum limit → 400 `INVALID_AMOUNT`
13. Verify transfer event published to the `transfers` Kafka topic with correct details
14. Verify idempotency key storage and expiration
15. Verify account ownership enforcement (can't transfer from another user's account)
16. Verify no sensitive data in logs or error messages
