# US-008: View transaction history

## User Story
**As an** authenticated account holder,
**I want to** view my transaction history,
**so that** I can track my account activity.

## Acceptance Criteria
- Given a valid access token, when I request my transaction history, then the system returns a paginated list of transactions.
- Each transaction includes: ID, type (debit/credit), amount in minor units, counterparty account ID, status, and timestamp.
- The list supports cursor-based pagination with deterministic ordering (newest first).
- Given an empty transaction history, when I request, then the system returns an empty list with a clear empty state.
- Given an invalid or expired access token, when I request history, then the system rejects the request.

## Technical Implementation Details

### API Endpoint
- **Method**: GET
- **Path**: `/api/v1/accounts/{accountId}/transactions`
- **Headers**: 
  - Authorization: Bearer <accessToken>
- **Path Parameters**:
  - `accountId`: UUID v7 of the account whose history is requested; it must belong to the authenticated user, otherwise the request is treated as not found
- **Query Parameters**:
  - `cursor`: string (optional) - pagination cursor from previous response
  - `limit`: integer (optional, default: 20, max: 100) - number of transactions to return
- **Success Response (200 OK)**:
  ```json
  {
    "transactions": [
      {
        "transactionId": "uuid (UUID v7)",
        "type": "string (debit | credit)",
        "amountCents": "integer",
        "counterpartyAccountId": "uuid (UUID v7)",
        "createdAt": "string (ISO 8601 UTC timestamp)"
      }
    ],
    "nextCursor": "string | null",
    "hasMore": "boolean"
  }
  ```
- **Error Responses** (error envelope `{"error":{"code","message","details","requestId"}}`):
  - 400 VALIDATION_ERROR: Invalid cursor or limit
  - 401 UNAUTHENTICATED: Missing or invalid access token
  - 401 TOKEN_EXPIRED: Access token expired
  - 404 ACCOUNT_NOT_FOUND: Account not found or not owned by the authenticated user

### Database Schema Changes
**Transaction Service Keyspace** (builds on US-007):
- Table: `transactions` (defined in US-007)
  - Columns:
    - `transaction_id` (UUID v7, primary key)
    - `account_id` (UUID v7, foreign key to accounts in account service)
    - `type` (text: debit or credit)
    - `amount_cents` (bigint)
    - `counterparty_account_id` (UUID v7, foreign key to accounts)
    - `created_at` (timestamp)
- Table: `transaction_timeline` (optimized for querying by account)
  - Columns:
    - `account_id` (UUID v7, partition key)
    - `created_at` (timestamp, clustering key - descending order for newest first)
    - `transaction_id` (UUID v7)
    - `type` (text)
    - `amount_cents` (bigint)
    - `counterparty_account_id` (UUID v7)
  - This table enables efficient queries for a specific account's transaction history

### Security Considerations
- Account ownership enforcement: Verify that the requested transactions belong to the authenticated user
- Data minimization: Only return necessary transaction fields, no sensitive account details
- Cursor-based pagination: Uses opaque cursors that cannot be tampered with to access other users' data
- Transaction immutability: Once recorded, transactions cannot be modified or deleted
- Consistent hashing: Cursor values are cryptographically signed to prevent tampering
- No sensitive data exposure: Transaction amounts and types are acceptable to share with account owner

### Error Handling
- Missing or invalid access token: Return 401 with error code `UNAUTHENTICATED` and message "Missing or invalid access token"
- Expired access token: Return 401 with error code `TOKEN_EXPIRED` and message "Access token expired"
- Invalid cursor format: Return 400 with error code `VALIDATION_ERROR` and message "Invalid cursor"
- Invalid limit value: Return 400 with error code `VALIDATION_ERROR` and message "Limit must be between 1 and 100"
- Account not found or not owned by the authenticated user: Return 404 with error code `ACCOUNT_NOT_FOUND` and message "Account not found" (avoids enumeration)
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`
- Service unavailable (e.g., Cassandra down): Return 503 with error code `SERVICE_UNAVAILABLE` and Retry-After header

### Pagination Implementation
- Uses token-based pagination with cryptographically signed tokens
- Cursor contains: accountId, timestamp, transactionId, and signature
- Server validates cursor signature and extracts paging parameters
- Query: SELECT * FROM transaction_timeline WHERE account_id = ? AND (created_at, transaction_id) < (?, ?) ORDER BY created_at DESC, transaction_id DESC LIMIT ?
- Response includes next cursor if more results exist
- Default limit: 20 transactions per page
- Maximum limit: 100 transactions per page (to prevent excessive resource usage)

### Test Cases
1. Valid request with proper access token → 200 OK with transaction list
2. Request with missing Authorization header → 401 Unauthorized
3. Request with invalid/malformed JWT → 401 Unauthorized
4. Request with expired JWT → 401 Unauthorized
5. Empty transaction history → Returns empty transactions array, nextCursor: null, hasMore: false
6. Single transaction in history → Returns array with one transaction
7. Multiple transactions → Returns correct number up to limit, ordered newest first
8. Pagination works correctly → Next cursor returns subsequent transactions
9. Cursor validity → Invalid or tampered cursor returns 400 Bad Request
10. Limit parameter respected → Returns exactly requested number (up to available)
11. Limit boundary conditions → Limit = 1 returns one item, limit = 100 returns up to 100
12. Limit validation → Values < 1 or > 100 return 400 Bad Request
13. Transaction types correct → Debit shown as negative amount context, credit as positive
14. Counterparty account ID present for all transactions
15. Timestamps in ISO 8601 UTC format
16. Deterministic ordering: Same timestamp transactions ordered by transaction_id
17. No transaction data leakage between accounts
18. Works correctly after account creation (empty history initially)
19. Reflects all completed transactions from successful transfers
20. Does not include pending transfers (only completed ones)
21. Concurrent requests return consistent results
22. Cursor-based pagination prevents duplicate or missing items across pages
