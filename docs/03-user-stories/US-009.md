# US-009: Prevent unauthorised account access

## User Story
**As the** system,
**I want to** enforce account ownership for every operation,
**so that** users can only access their own accounts.

## Acceptance Criteria
- Given an authenticated user, when they attempt to access another account's balance, then the system rejects the request with a 404 error.
- Given an authenticated user, when they attempt to initiate a transfer from another account, then the system rejects the request with a 404 error.
- Given an authenticated user, when they attempt to view another account's transaction history, then the system rejects the request with a 404 error.
- Automated negative tests verify that users cannot access another account's data.
- All API endpoints except `POST /api/v1/register`, `POST /api/v1/login`, `POST /api/v1/refresh`, and the gateway health endpoints (`GET /healthz`, `GET /readyz` at the root, outside `/api/v1`) require valid authentication.

## Technical Implementation Details

### Authentication Middleware
- **Location**: API Gateway (centralized enforcement)
- **Process**:
  1. Extract JWT from Authorization header
  2. Validate token signature, expiration, issuer, and audience
  3. Extract user identifier (`userId`) from token claims
  4. Attach user context to request for downstream services
  5. If token invalid or missing, return 401 UNAUTHENTICATED immediately

### Authorization Enforcement by Service
Each service must verify that the authenticated user owns the resource being accessed:

#### Account Service
- **Balance Access (`GET /api/v1/accounts/{accountId}/balance`)**:
  - Verify the `accountId` path parameter matches the authenticated user's account
  - On mismatch, return 404 `ACCOUNT_NOT_FOUND` (never 403) to avoid enumeration

#### Transfer Service
- **Transfer Initiation (`POST /api/v1/transfers`)**:
  - The source account is the authenticated user's account, resolved from the auth context; the client cannot supply `sourceAccountId`
  - Destination account validation: Check if account exists (without revealing existence to unauthorized users)
- **Transfer Status (`GET /api/v1/transfers/{transferId}`)**:
  - Verify authenticated user owns either `sourceAccountId` or `destinationAccountId` of the transfer
- **Implementation**:
  ```python
  # Pseudocode for authorization check
  user_account_id = get_account_id_from_auth_context(request)
  # The source account IS the authenticated user's account; clients never supply one.
  source_account_id = user_account_id

  # For status checks
  transfer = get_transfer(request.transferId)
  if transfer.sourceAccountId != user_account_id and transfer.destinationAccountId != user_account_id:
      raise NotFoundError("Transfer not found")
  ```

#### Transaction Service
- **Transaction History (`GET /api/v1/accounts/{accountId}/transactions`)**:
  - Verify the `accountId` path parameter matches the authenticated user's account
  - On mismatch, return 404 `ACCOUNT_NOT_FOUND`
- **Implementation**: Service queries transaction_timeline using the verified account id from auth context

### Database Schema Changes
No additional schema changes required - authorization is enforced at the service level using existing account relationships.

### Security Considerations
- Defense in depth: Authentication at API Gateway, authorization at each service
- Consistent user identity propagation: Securely pass user context between services
- Principle of least privilege: Services only access data necessary for their function
- Account ownership verification: Always verify both ends of a relationship (for transfers: check both source and destination ownership as appropriate)
- Error message normalization: Return 404 for both "not found" and "not authorized" to prevent account enumeration
- Timing attack prevention: Authorization checks should take consistent time regardless of outcome
- Session integrity: Ensure user context cannot be tampered with between gateway and services
- Service-to-service authentication: For inter-service calls, use service accounts or signed JWTs

### Error Handling
- Missing or invalid access token: Return 401 with error code `UNAUTHENTICATED` and message "Missing or invalid access token" (handled by API Gateway)
- Expired access token: Return 401 with error code `TOKEN_EXPIRED` and message "Access token expired" (handled by API Gateway)
- Account authorization failure: Return 404 with error code `ACCOUNT_NOT_FOUND` and message "Account not found" (consistent across all services to prevent enumeration)
- Transfer authorization failure: Return 404 with error code `TRANSFER_NOT_FOUND` and message "Transfer not found" (consistent across all services to prevent enumeration)
- Internal server errors: Return 500 with error code `INTERNAL_ERROR`

### Test Cases
1. Valid access to own account balance → 200 OK
2. Attempt to access another user's balance → 404 Not Found
3. Valid transfer from own account → 202 Accepted (if all other conditions met)
4. Attempt to initiate a transfer and smuggle a foreign `sourceAccountId` (or any unknown field) in the body → 400 `VALIDATION_ERROR`; the source account is always the JWT-derived account
5. Valid access to own transaction history → 200 OK
6. Attempt to access another user's transaction history → 404 Not Found
7. Valid transfer status check for own transfer → 200 OK
8. Attempt to check status of transfer belonging to another user → 404 Not Found
9. Missing Authorization header → 401 Unauthorized
10. Invalid/JWT token → 401 Unauthorized
11. Expired JWT token → 401 Unauthorized
12. Tampered JWT token → 401 Unauthorized
13. Concurrent access attempts → Each properly authorized or rejected
14. Cross-service authorization checks → All services enforce ownership appropriately
15. Verify no account information leakage in error messages (all return generic "not found")
16. Automated negative test suite attempts all combinations of unauthorized access
17. Service-to-service calls properly authenticated
18. Public endpoints (register, login, refresh, healthz, readyz) accessible without JWT authentication
19. All other endpoints require valid JWT
20. Verify user context propagation maintains integrity across service boundaries

### Dependencies
- API Gateway (for authentication)
- Auth Service (for user account information)
- All domain services (Account, Transfer, Transaction) for authorization enforcement
- Cassandra databases for user and account data
